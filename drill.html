7.3 · Hooks

Item 1 · D7

A team runs Claude Code unattended in CI. Policy requires that any Bash invocation matching a deny-list never executes, and no human is available to approve or reject anything during the run.

Which mechanism enforces this?

  1. A PreToolUse hook that exits 2
  2. A permission prompt configured to auto-deny
  3. A prohibition written into CLAUDE.md
  4. An inference hook registered on the prompt event
Answer

A · D7 / 7.3 — exit 2 is a blocking error on a blocking-capable event, and the hook fires whether or not anyone is watching.

B — permission prompts are the interactive approval path. Headless means no Operator seat exists to prompt.

C — CLAUDE.md is context the model reads. That's persuasion, not enforcement.

D — inference hooks are server-side and Enterprise-only, fire only on prompt, and never see a tool call.

Rule: unattended + must-never-happen = Architect-seat hook, never Operator-seat permission.

Item 2 · D7

A developer is reviewing a colleague's description of how Claude Code hooks work before signing off on a security design.

Which statement is accurate?

  1. Every handler is a shell command, so a hook can never invoke a model
  2. Handler types include command, http, mcp_tool, prompt, and agent
  3. Handler types include command, http, and function (a TypeScript module)
  4. The harness selects the handler type automatically based on the event
Answer

B · D7 / 7.3 — five handler types, and two of them delegate the decision to a model.

A — the common overstatement, and the one the grid itself got wrong. prompt and agent handlers judge.

C — "function"/module handlers are a GitHub proposal, not shipped. Classic fake-mechanism distractor.

D — you declare the handler.

Rule: the firing is deterministic; the verdict need not be. The checkpoint always stops you — who staffs it is your choice.

Item 3 · D7

A team wants a log line written every time the agent edits a file. The edit itself must proceed unchanged.

Which fits?

  1. A PostToolUse hook
  2. A PreToolUse hook returning exit 2
  3. A permission prompt
  4. Context editing
Answer

A · D7 / 7.3 — observe after the fact, change nothing.

B — exit 2 blocks, which the stem forbids.

C — inserts a human and can change the outcome.

D — clears tool results from context; nothing to do with logging.

Rule: gate before = PreToolUse. Observe after = PostToolUse.

Item 4 · D7

An enterprise must allow or deny every prompt submitted across the organization, enforced centrally on the server, with a binary verdict, regardless of which client the developer uses.

Which mechanism?

  1. Inference hooks
  2. A UserPromptSubmit hook in settings.json
  3. Permission modes
  4. A PreToolUse hook
Answer

A · D7 / 7.1 vs 7.3 — server-side, Enterprise, only event is prompt, verdict binary, cannot rewrite.

B — client-side and per-machine. A developer using a different client bypasses it entirely.

C — governs tool approvals, not prompt admission.

D — tool-scoped, and also client-side.

Rule: "server-side + every prompt + binary + enterprise" = inference hooks. Different product that shares a word.

Item 5 · D7

A hook must return a structured decision — a denial carrying a reason the model can read — rather than a bare pass/fail.

How?

  1. Exit 0 and emit JSON on stdout
  2. Exit 2
  3. Exit 1
  4. Set a decision field in settings.json
Answer

A · D7 / 7.3

B — exit 2 is the blocking error: it stops the call but isn't the structured channel.

C — a non-blocking error.

D — settings.json registers hooks; it doesn't carry per-invocation verdicts.

Rule: exit 2 = block. Exit 0 + JSON = decide, with reasons.

1.2 · Agent construction

Item 6 · D1

A team needs an agent that fires nightly on a schedule, keeps a workspace with file state across runs, and whose configuration is versioned so each session pins to a known version.

Which is the lowest-complexity option that meets all three?

  1. Managed Agents with a scheduled deployment
  2. The Claude Agent SDK on a cron job on their own VM
  3. The Tool Runner invoked from a scheduled function
  4. A manual loop with state persisted to object storage
Answer

A · D1 / 1.2 — scheduling, persistence and versioning are all deployment concerns, and Managed Agents is the only option that supplies deployment.

B, C, D — all three are harness-only. Each leaves you owning the scheduler, the workspace and the config store. They're not wrong mechanisms, they're more work.

Rule: "theirs" to both questions — whose loop, whose premises — is Managed Agents alone.

Item 7 · D1

An architect is classifying the options by what infrastructure the team will still have to own.

Which TWO supply a harness but leave deployment to you? (Select TWO)

  1. The Tool Runner
  2. Managed Agents
  3. The Claude Agent SDK
  4. The Messages API with no tools declared
  5. Inference hooks
Answer

A and C · D1 / 1.2

B — supplies harness and deployment. That's the whole distinction.

D — a single call is not a harness at all; there's no loop.

E — a security mechanism, not an agent-construction surface.

Rule: A and C share a quadrant. That shared square is exactly why they're confusable.

Item 8 · D1

A team wants a coding agent with built-in file read/write/edit, bash, and grep, running on infrastructure they control.

Which?

  1. The Claude Agent SDK
  2. The Tool Runner
  3. Managed Agents
  4. The Messages API with the Anthropic-defined bash tool
Answer

A · D1 / 1.2 — the Agent SDK is Claude Code as a library: full harness plus the built-in toolset, hosted by you.

B — same quadrant, but it ships zero built-in tools. You'd write every one.

C — hosts it for you, which the stem rules out.

D — the bash tool is real and schema-less, but you'd still hand-write the loop and every other tool.

Rule: when two options sit in the same 2×2 square, the tiebreak is does it arrive with tools?

Item 9 · D1

A team is deciding whether to hand-write the agent loop instead of using the Tool Runner.

Which is a valid reason to hand-write it?

  1. The required control flow doesn't fit the Tool Runner's per-turn hooks, or they won't take a beta dependency
  2. They need built-in filesystem tools
  3. They need Anthropic to host the tool-execution sandbox
  4. They need an approval gate before each tool executes
Answer

A · D1 / 1.2 & 2.4

D — the trap, and the one the grid originally failed. Per-turn hooks in the Tool Runner already give approval gates, logging, error interception, result modification and retries. Wanting a gate is not a reason to hand-roll.

B — that's the Agent SDK.

C — that's Managed Agents.

Rule: hand-rolling buys control flow, not features. If you can name the feature you want, the Tool Runner probably has it.

1.3 · Agent patterns

Item 10 · D1

Incoming support tickets must be classified and then handled by one of four specialized prompts. The four categories are known, stable, and unlikely to change.

Which pattern?

  1. Routing
  2. Orchestrator-workers
  3. Parallelization
  4. Evaluator-optimizer
Answer

A · D1 / 1.3 — known set, exactly one branch taken.

B — decomposition decided at run time. Here it's fixed in advance.

C — known set, but all branches fire.

D — requires a critique loop; there isn't one.

Rule: known options + pick one = routing. Known options + do all = parallelization.

Item 11 · D1

A research task must be broken into subtasks that cannot be enumerated ahead of time — their number and nature depend on what earlier steps turn up.

Which pattern?

  1. Orchestrator-workers
  2. Routing
  3. Prompt chaining
  4. Parallelization
Answer

A · D1 / 1.3 — "cannot be enumerated ahead of time" is the giveaway: the split happens at run time.

B, C, D — all three require the shape to be known before the run. Each is a workflow, not an agent.

Rule: decomposition before the run → workflow. During the run → orchestrator-workers. This is the Architect/Operator line.

Item 12 · D1

A translation is drafted, scored against a rubric, and revised — repeating until it clears the bar.

Which pattern?

  1. Evaluator-optimizer
  2. Prompt chaining
  3. Orchestrator-workers
  4. Routing
Answer

A · D1 / 1.3 — the only pattern with an arrow pointing backwards.

B — sequential but one-pass; nothing returns.

C — delegates outward; doesn't critique its own output against a bar.

D — dispatch, no loop.

Rule: a critique that feeds back = evaluator-optimizer. Draw it: it's the only cycle.

Item 13 · D1

A team is documenting whether a given design is a workflow or an agent.

Which TWO indicate a workflow? (Select TWO)

  1. The sequence of steps is fixed before the run
  2. The model chooses which tools to call, and when
  3. Each step's output feeds the next, wired in code
  4. The number of iterations depends on what the model finds
  5. The task is open-ended and hard to fully specify
Answer

A and C · D1 / 1.1 & 1.3 — both describe paths laid down in advance.

B, D, E — all three hand path-selection to the model at run time. That's the definition of an agent.

Rule: the train runs on rails you laid. The taxi picks the route. Ask only: who chooses the next step?

5.4 · Cost and token management

Item 14 · D5

A service makes many near-identical requests. The system prompt is a frozen constant and the messages differ only in the final user turn, yet cache_read_input_tokens is zero on every request. The tool list is serialized from a dictionary at call time.

What is the most likely cause?

  1. Tool serialization order varies between requests, invalidating everything after it
  2. The final user turn differs, which invalidates the prefix
  3. Four breakpoints is not enough for this request shape
  4. Caching requires the beta header and it isn't set
Answer

A · D5 / 5.4 — tools renders first. A nondeterministic tool order changes the lowest plate on every request, so nothing above it can ever match.

B — messages render last. A varying final turn is normal and is exactly what you want above the breakpoint.

C — the 4-breakpoint cap is real, but exceeding it isn't what drives a rate to zero.

D — prompt caching is not gated behind a beta header.

Rule: rate at zero → suspect the lowest plate. Order is tools → system → messages.

Item 15 · D5

Midway through a long conversation, an operator instruction must be added. The cached prefix must survive, and the instruction must not be reachable by content in the conversation.

Which approach?

  1. Append a system-role message to the messages array
  2. Edit the top-level system field
  3. Add another cache_control breakpoint
  4. Enable context editing to clear older turns first
Answer

A · D5 / 5.4 & D7 / 7.1 — a mid-conversation system message is a new plate on top. It preserves the cached prefix and is the injection-safe operator channel.

B — system renders below messages. Editing it drops everything above. Same instruction, opposite cache outcome.

C — breakpoints mark what to cache; they don't protect a prefix you just changed.

D — clears tool results and thinking. Doesn't add an instruction.

Rule: add a plate on top; never swap one underneath. One mechanism answers both the caching question and the injection question.

Item 16 · D5

An agentic loop must wind up cleanly inside a token allowance — summarizing and concluding rather than stopping mid-output.

Which mechanism?

  1. A task budget in output_config
  2. A lower max_tokens
  3. A Managed Agents session budget
  4. effort: "low"
Answer

A · D5 / 5.4 — the server injects a countdown the model can see, so it paces itself and lands. Advisory, token-denominated.

B — an enforced per-response ceiling the model is not aware of. It truncates, which is precisely what the stem rules out.

C — real, but dollar-denominated, hard, platform-enforced, and Managed Agents only. It stops you; it doesn't help you finish.

D — reduces thinking depth and spend but sets no ceiling and produces no graceful landing.

Rule: two axes — is the model told, and what unit? Told + tokens = task budget.

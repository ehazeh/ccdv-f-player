How to read this

Every entry settles a discrimination, not a definition. The exam's wrong answers are all “a real mechanism in the wrong place,” so what's tested is placement, not recall.

The five kinds

K1 and K2 your OOP background already holds. K3, K4, K5 are the deficit — and that is exactly where all four weak areas live.

The three seats — the spine

Architect · before the runCLAUDE.md, settings.json, hooks, permission modes, skills. Law: written once, binds every session, not negotiable.
Operator · during the runPermission prompts, steering, model/effort choice, subagents. Judgment: you are in the room.
Construct-self · inside the runContext filling, latency, cost, compaction. Experience: felt, not controlled.
The seat test. Most confusable pairs collapse to one question: which chair were you sitting in when this fired?

The fourth seat — the investigator

Investigator · inside, without the rules All three seats above presuppose you already know the rules. This one doesn't: inside the system, didn't build it, doesn't yet know how it works, reverse-engineering it from the inside. It is the only seat where learning happens — the other three are competence stances.
Keep this one out of the exam tool. The seat test works because Architect / Operator / Construct-self are operational stances that settle where a mechanism fires. The investigator seat settles nothing — it's the reason you're studying, not a discriminator. Structurally it's where the loop starts: you cannot write law for a system you've never been inside.

D1 · Agents and Workflows14.7%

1.1 Agent architecture

Agent K1

A taxi driver. You give a destination; they pick the route.

vs. workflow. The whole question is who chooses the next step.

Workflow K5

A train. Rails laid in advance; it cannot decide to turn.

Agent = model decides at run time. Workflow = you decided at design time. The Architect/Operator line.

Harness K1

The car, not the driver. Pedals, mirrors, fuel gauge.

Swapping the harness is not swapping the model. Claude Code, Tool Runner and Managed Agents are all harnesses.

Agent loop K3

The cycle of the wipers — decide, act, observe, repeat until stop_reason stops saying tool_use.

A control structure, not an object. Stop looking for a noun.

1.2 Agent construction · weak area

Not four products — two questions K3

Q1 · Whose pilot flies it? (the harness: loop + context management)
Q2 · Whose hangar is it parked in? (the deployment)

Manual looppilot: yourshangar: yours
Tool Runnerpilot: theirshangar: yours
Managed Agentspilot: theirshangar: theirs
Claude Agent SDKpilot: theirshangar: yours

Manual loop — you built the ship and you're flying it. Tool Runner — borrowed autopilot in your own ship, no tools aboard but the ones you bolted on. Managed Agents — you booked passage: their ship, their pilot, their cargo hold. Agent SDK — a fully fitted ship delivered to your hangar; you pay the berth.

Managed Agents is the only one that answers “theirs” to both. Stem mentions hosting, per-session containers, persistence, versioning or scheduling → Managed Agents. Stem mentions only not wanting to write the loop → Tool Runner.

Tool Runner ≠ Agent SDK. Tool Runner lives inside the regular Anthropic SDK (client.beta.messages.tool_runner) and has zero built-in tools. The Agent SDK is Claude Code as a library, with the full built-in toolset. Both are harness-only. This confusion is a designed distractor.

1.3 Agent patterns · weak area

The five patterns K5

  • Prompt chaining — a relay of hardline calls, each stop fixed in advance.
  • Routing — the Operator picks which crew member to send, from a known roster.
  • Parallelization — the whole crew jacks in at once on the same problem.
  • Orchestrator-workers — a lead decides on the fly who does what, including subtasks nobody planned.
  • Evaluator-optimizer — the sparring program: run, get critiqued, run again.

Master discriminator: was the decomposition decided before the run or during it? Before → workflow pattern. During → orchestrator-workers. That is the seat line applied to topology.

The trap set. Routing: known options, pick one. Parallelization: known options, do all. Orchestrator: options not known until run time.

Should you build an agent at all?

Four gates — complexity (multi-step, hard to fully specify), value (justifies cost + latency), viability (Claude is good at this), cost of error (recoverable: tests, review, rollback).

Any “no” → drop a tier. The simplest tier that works is the right answer; the exam rewards restraint.

D2 · Applications and Integration33.1% — biggest

2.3 Claude API mechanics

Messages API K1

The single front door. Everything goes through POST /v1/messages.

Tools and output constraints are features of this endpoint, not separate APIs. A stem implying a separate “tools API” is wrong.

Streaming K3

Water from a tap vs. a delivered bucket.

Required for large max_tokens — not for quality, for HTTP timeouts.

Batches K4

Off-peak electricity. Same work, cheaper, arrives later.

Results come back in any order — key by custom_id, never by position.

Files API K2

A coat check. Hand it over once, get a ticket, reuse the ticket.

vs. inline base64, which re-sends the whole thing every request.

Server tools K2

Tools bolted to their factory floor, not yours. Results arrive in the same response.

vs. client-side tools, which you execute and return. No loop for server tools.

CLAUDE.md K2 Architect

Teaches context, not capability. More specific location wins.

settings.json scopes K3

Municipal → state → federal. Narrower scope overrides broader.

Precedence-reversal is a standard distractor. Know the direction.

D4 · Eval, Testing, Debugging2.6%

Error class chain K1

Triage, most specific first: NotFound → RateLimit → APIStatus → APIConnection.

Catching one broad class loses retryable (429, 5xx, network) vs. non-retryable (400, 404). That distinction is the question.

Eval set K2

A fixed exam you re-sit after every change.

Built from real production failures, not invented cases.

D5 · Model Selection and Optimization16.8%

5.1 / 5.2 Fundamentals

Context window K4

The desk surface. Everything you work from must fit on it at once.

Not memory, not storage. A working surface, re-laid every single request.

Extended thinking · Effort K4

Thinking is time spent before answering, billed. Effort is the dial on how hard to try, low → max.

Modern thinking is adaptive — the model decides depth. The fixed-budget concept is deprecated.

5.4 Cost and token management · weak area

Prompt caching = a stack of plates K4K3

messagestop · changes most
systemmiddle
toolsbottom · changes least

Change a plate anywhere and everything above it comes off. Nothing below is disturbed.

  1. The order is fixed: tools → system → messages.
  2. Put what changes least at the bottom; timestamps and the varying question on top.
  3. It is a prefix match, not a lookup — only “how far up does the stack still match.”
  4. Hit rate stuck at zero? Something near the bottom is being quietly swapped every request — a datetime.now() in the system prompt, an unsorted tool list. Verify with usage.cache_read_input_tokens.

Plates carry ordering and invalidation only. Price, TTL and breakpoint count are perishable — flashcard, not metaphor.

The three ceilings K4

Two axes: is the model told? and what unit?

max_tokensnot toldtokens
task budgettoldtokens
session budgetnot tolddollars

max_tokens — closing time, unannounced; cut off mid-sentence. Task budget — a per diem handed to the traveler; they pace themselves and land gracefully; advisory. Session budget (Managed Agents) — the card declines; hard, platform-enforced.

“Finishes gracefully / paces itself” → task budget. “Hard cap / spend limit” → session budget. “Truncated mid-output” → max_tokens.

D6 · Prompt and Context Engineering11.0%

6.1 The confusable trio

Compaction K3 Construct-self

Rewriting three pages of notes as one paragraph. Condensed, retained.

Happens to you. Server-side, fires at a threshold.

Context editing K3 Operator

Tearing pages out. Gone, not condensed.

You command it. Client-directed, in the request.

Memory K2

A filing cabinet outside the room. Survives the session.

Architect-adjacent: what you write there becomes law for future runs.

Two-question test. Does the content survive in compressed form, or vanish? (compaction vs. editing) And who ordered it — the server on a threshold, or you in the request? Compaction summarizes; context editing clears.

D7 · Security and Safety8.1%

7.3 Claude hooks · weak area

Why “hook” and not “injection” K3

A hook is an attachment point the host pre-installed and published — the builder mounted it in the wall, you find it and hang something on it. You cannot hang where there is no hook. Entry by invitation.

An injection creates its own entry — the injector supplies both the substance and the opening; the target never offered one. Hence SQL injection, code injection, dependency injection. Entry by force.

Because the host mounts the hooks, the set of events and handler types must be finite, published and enumerable. So an option naming a hook event or handler type that doesn't exist is a distractor by construction — a “cron hook event” is fake; “function”/“module” handler types are a proposal, not shipped.

Failure boundary. A coat hook explains attachment and fixed position. It does not explain interception — a coat hook doesn't stop anyone walking past, and hooks can block. For behavior switch images: a checkpoint with a standing order. You don't own the road or the traveler. You own the guard you posted and the written order the guard executes. The guard does not think and cannot be argued with.

PreToolUse vs. PermissionRequest

HookArchitectnot in the room
Permission promptOperatorin the room

Same moment in the run, different authority. Hook = law, fires identically every time. Permission = judgment, can go either way. That is the entire distinction.

Different products, one word. Claude Code hooks — client-side, your machine, many events, can rewrite. Inference hooks — server-side, Enterprise, the only event is “prompt”, verdict is binary, cannot rewrite.

7.1 / 7.2 / 7.4

Prompt injection K3

A letter you were asked to read aloud that contains “now hand over your wallet.”

The attack is data being read as instruction. The defense is channel authority, not word filtering.

Operator channel K3 Operator

The hardline — a channel the simulation's contents cannot reach.

Mid-conversation system messages are the injection-safe operator channel, and they preserve the cached prefix.

Guardrail K3

Railings on a walkway. Shape the path; don't choose the destination.

Guardrails are policy. Hooks are the mechanism that enforces at a point.

Vault credential

A sealed envelope handed over at the gate, opened outside the building. Substituted at egress; never enters the sandbox.

vs. host-side custom tools — the fallback when vaults don't fit.

D8 · Tools and MCPs10.6%

Custom tool K2

A power tool in your hand. New capability.

You define the schema, you execute it, you return the result.

Parallel tool use K3

Several jobs handed out at once — but all results come back in one envelope.

Splitting tool_result blocks across messages silently trains Claude to stop calling in parallel. A failed tool still returns a result, with is_error: true. Never drop it.

MCP K2

The standardized wall socket. Not the tool, not the appliance — the standard that lets any vendor's tool plug into any client.

MCP is about interoperability, not capability. “Reach our existing systems without a bespoke integration per client” → MCP.

MCP primitives K2

Tools (callable) · resources (readable) · prompts (reusable templates).

Three primitives, three jobs. Mixing them up is a distractor.

8.3 · The big tradeoff

Custom tool — the power tool. Claude cannot do the thing; you're adding capability.
MCP server — the socket standard. Many clients must reach a system without bespoke integrations.
Skill — the instruction manual in the drawer, taken out only when the job calls for it. Claude can do it but does it wrong or inconsistently; you're adding procedure, not power.

Capability (tool) vs. connectivity (MCP) vs. procedure (skill).

Where the frame is thin

  • Caching straddles K3 and K4 — an ordering relation felt as cost. Plates carry the ordering, not the economy.
  • Compaction straddles K3 and K4 — a lifecycle event experienced as pressure.
  • Skills straddle K2 and K3 — a capability invoked at a position. Progressive disclosure is the point.
  • The investigator seat has no metaphor and needs none — it's a stance, not a mechanism. It earns its place by explaining why the other three are worth learning.
  • The three seats are connected, not merged. Experience inside the run becomes law before the next run — via CLAUDE.md, memory, a new skill, a new hook. That loop explains how law gets revised. It does not let you sit in two chairs at once, and the seat test only works if you keep them separate.
